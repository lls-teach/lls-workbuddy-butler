# 互联网取数层（Net）

**能力层方法论借鉴 Panniantong/Agent-Reach（MIT），文本独立重写。**

**核心理念**：lhg-net 是"眼睛"，不是"脑子"。它的全部工作是把互联网公开内容取回来——搜得到、抓得全、来源可查；分析、判断、写成文章是别人的活（lhg-deep-research / lhg-trend / lhg-writing）。眼睛越干净，脑子越好使。

**平台中立**：全文只用通用能力描述——联网搜索、抓取全文、只读子 agent、任务清单、文件搜索/编辑，不依赖任何单一平台的专有工具名，不出现原版的专有调用名。

---

## 1. 触发与 NOT for（先定边界，再动手）

### 1.1 何时用 lhg-net

用户要的是"把某处公开内容取回来"，典型说法：

- "帮我搜一下 B 站/小红书/微博上关于 X 的内容"
- "这个网页/这篇文章全文抓下来"
- "这个视频的字幕拉出来"
- "看看某话题在各平台的讨论情况"（只收集，不下结论）
- "某账号/UP 主最近发了什么"
- "GitHub 上这个项目/issue 的内容"

### 1.2 NOT for 清单——这些不归眼睛管

| 用户真实需求 | 该走的 skill | 误触发会怎样 |
|---|---|---|
| 开放式调研/深度分析（"研究一下 X 的来龙去脉/给我个结论"） | lhg-deep-research | 眼睛只会堆链接，给不出分析框架 |
| 热点选题/找灵感（"最近有什么热点可以写"） | lhg-trend | 眼睛不懂热度排序和选题价值 |
| 写作/改写/润色 | lhg-writing | 取数 skill 不管文字质量 |
| 写代码/工程规范 | lhg-craft | 完全无关 |
| 系统化调试 | lhg-debug | 完全无关 |

**误触发处理**：请求看起来像"取数+分析"混合时，先声明分工再开工——"取数走 lhg-net，分析走 lhg-deep-research；我先取数，取完把 raw 材料交过去。"不许眼睛顺手把分析也做了。

## 2. 平台后端链（中文优先）

每个平台都是一条**有序后端链**：首选 → 备选 → 纯流程降级。接入方式变了（比如某工具没装、某接口挂了），只调链上顺序，不重写流程。

### 2.1 中文平台（一等公民）

| 平台 | 首选 | 备选 | 纯流程降级 |
|---|---|---|---|
| 抖音 | 宿主已装的只读短视频工具 | 网页版搜索直取 | 联网搜索（限定站点）+ 抓取全文 |
| 微博 | 公开热搜/话题接口 | 网页版直取 | 联网搜索 + 抓取全文 |
| B 站 | 公开 API（搜索/视频信息） | 网页版直取 | 联网搜索 + 抓取全文；字幕：宿主字幕工具 → 网页字幕接口 → 降级为简介+评论 |
| 小红书 | 宿主已装的只读笔记工具（需登录态） | 网页版（需登录态） | 联网搜索笔记标题+摘要（必须声明覆盖不全） |
| 雪球 | 公开帖子/行情接口 | 网页版直取 | 联网搜索 + 抓取全文 |
| V2EX | 公开 API | 网页版直取 | 联网搜索 + 抓取全文 |
| 小宇宙 | 节目公开页/RSS | 网页版直取 | 联网搜索单集标题+简介 |
| 微信公众号 | RSS 订阅源（已订阅） | 公众号网页版 | 通用微信文章搜索 + 抓取全文（声明可能不全） |

### 2.2 英文平台（保留）

| 平台 | 首选 | 备选 | 纯流程降级 |
|---|---|---|---|
| Twitter/X | 宿主已装的只读工具 | 网页版/公开镜像 | 联网搜索 + 抓取全文 |
| Reddit | 公开 JSON 接口 | 网页版直取 | 联网搜索 + 抓取全文 |
| YouTube | 宿主字幕工具 | 网页版直取 | 联网搜索 + 抓取全文；字幕取不到时降级为简介+评论 |
| GitHub | 宿主代码托管 CLI | 公开 API | 网页版直取 |
| HN | 公开 API | 网页版直取 | 联网搜索 + 抓取全文 |
| LinkedIn | 宿主已装的只读工具（需登录态） | 公开帖子网页版 | 联网搜索（覆盖有限，必须声明） |

### 2.3 后端链三条铁律

1. **顺序即策略**：永远从链头开始试，坏了往后走，不许跳过"可用"的去用"顺手"的。
2. **降级要声明**：用到"纯流程降级"或"覆盖不全"的备选时，在交付物里写清楚"本次 via 降级链，覆盖范围：…"。
3. **换接入只调序**：某后端新增/失效，只改该平台链上的顺序，不动第 3–6 节的流程。

---

## 3. 工具→流程双轨制

这是本 skill 相对原版的核心加持：**有工具走工具链，没工具走纯流程，零外部依赖也能跑**。

- **工具轨**：宿主环境装了对应只读工具（搜索工具、字幕工具、代码托管 CLI 等）时走工具链，速度快、结构好。
- **流程轨**：无工具/容器/受限环境时走纯流程三步：① 联网搜索定位目标 URL → ② 抓取全文提取正文 → ③ 平台公开 API/网页版直取补全。
- **判定方式**：动手前先做第 4 节的"能力体检"，探测结果决定走哪条轨——不许凭感觉假设"工具肯定装了"。

---

## 4. 能力体检（doctor，动手前必做）

对本次任务用到的平台，按后端链顺序做**真实探测**，不许跳过。

1. **轻量探针**：每个候选后端发一次最小探测（如公开 API ping 一下、搜一个词看返回是否非空）。探针只读，不发帖、不写入、不触发登录。
2. **选第一个完整可用的**：链上第一个探测通过的后端成为本次的"选用后端"。
3. **坏掉的给修复处方**：探测失败的后端，一句话写清"缺什么、怎么装/配、去哪看文档"，不瞎猜、不编命令。
4. **未探测 ≠ 不可用**：为避免触发浏览器 Cookie 读取或远端写入而跳过实时探测的后端，只是不确定，不代表它不存在；任务真需要该平台时，再用只读命令手动验证一次。

---

## 5. 常驻规则（全程适用）

1. **动手前先体检**：第 4 节的探测是开工前置条件，跳过体检直接取数=违规。
2. **开工先声明**：开始干活前说一句——"取数用 lhg-net：X 平台 / Y 后端（工具轨/流程轨）"。让用户知道你走的哪条路。
3. **失败按重试链处理**：本级后端失败 → 下一级后端 → 纯流程降级 → 诚实报告"取不到"。**不瞎猜命令**，不编造"我大概能这样取"。
4. **多平台任务并行收集再汇总**：需要跨平台时，各平台独立收集（可用只读子 agent 并行跑），全部取回后再做一次"取数汇总"。汇总只列"取回了什么"，不下分析结论。
5. **只取数，不分析**：交付物是"取回了什么 + 来源 + 时间"，任何"这说明…"的判断都留给调用方（lhg-deep-research 等）。

---

## 6. 取数交付物格式

每次取数结束，输出固定三段：

- **取回了什么**：条目清单（标题/摘要/关键字段），注明 via 哪条后端链、工具轨还是流程轨。
- **来源与时间**：每条给 URL + 抓取时间；覆盖不全的写清缺口。
- **未覆盖**：哪些平台/后端没跑通、原因是什么（附修复处方），不隐瞒。

---

## 7. 安全默认

- **只读不发帖**：不点赞、不评论、不转发、不私信、不关注。取数 skill 永远不做写入动作。
- **Cookie 只存本地**：登录态文件不进仓库、不上传、不贴到对话里给别人看。
- **登录态建议用小号**：需要登录的平台优先用小号；动主号登录前必须用户明确授权。
- **遵守速率限制**：被限流/封禁迹象出现时立即停手，报告现状，不换 IP 硬闯。

## 自检与反馈（自迭代协议 v1.0）

1. **每次运行后轻量自检**：对照"NOT for 清单 / 后端链顺序 / 常驻规则 / 安全默认"，检查本次执行是否违反硬性规则（如：开放式调研顺手做了分析、跳过体检直接取数、失败时瞎猜命令、做了写入动作）。
2. **怀疑自身问题时跑冒烟测试**：如果自检发现可能是 skill 自身缺陷（如某平台后端链顺序过时、NOT for 边界不清），运行 `references/smoke-test.md` 标准用例。
3. **输出质检报告**：问题描述 + 冒烟测试结果 + 修改方案（具体到 SKILL.md 的哪一节、建议怎么改）。
4. **问题反馈**：质检报告经用户确认后，由用户通过 WorkBuddy 资产页联系作者反馈问题。
5. **修复后重测**：按用户确认的方案修改，跑冒烟测试全绿后随更新版本交付。
