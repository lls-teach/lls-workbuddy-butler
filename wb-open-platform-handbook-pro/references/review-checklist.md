## ⚡ 解析器实测规则（2026-10-24 发布实测，比官方文档严格）

- zip ≤3MB；**仅支持两级目录**（根目录/二级目录/文件）——`.github` 等三层嵌套直接报"目录层级超限"
- frontmatter **必含 `display_name`（中文）与 `display_name_en`（英文）**
- frontmatter 值含"英文冒号+空格"必须整体加引号，否则 YAML 解析失败（报 mapping values are not allowed）
- 上传解析通过即生成技能 ID（os_xxx）；审核中可撤回回草稿；向导中途离开自动存草稿（zip/分类回填）
- 头像需走过"继续"才落库；发布表单的"试试这样问我"来自 frontmatter examples_zh

提交审核前逐项自检，可显著降低驳回率。

## 🚫 强制下架红线（发布后巡查，2026-10-26 实锤）

依据《开发者公约》第 2.8.3 条「服务安全与接口使用」，以下类型即使过审也会被**强制下架**：

- ❌ 以自动化方式替代用户真实操作，**获取平台活动权益**（自动签到领积分、自动领取活动奖励、刷权益类功能）
- ❌ 绕过平台接口或活动规则获取权益的功能设计

**实例**：WorkBuddy 签到助手 v3.3.0（os_cbec45dcae805e36）过审并发布后，2026-10-26 被强制下架，官方理由即上述条款。下架卡片提供「下架原因」与「联系运营」入口。

**关键教训**：**审核通过 ≠ 长久安全**——平台有发布后巡查。体检时对"自动签到/自动领取/批量获取权益"类功能要直接预判强制下架，建议改为提醒用户手动领取等不触碰权益发放秩序的设计。

## 驳回后处理

按页面提示原因修改 → 重新提交（应用 ID 不变）。zip 解析失败：对照结构自查 → 仍失败邮件 openworkbuddy@tencent.com 或官方社群。审核期间的资产状态：审核中/已启用/已驳回。

**强制下架后处理（区别于驳回）**：先看下架原因原文确认触条，不要原功能换名重提；按提醒型/查询记录型/手动确认型重做功能定位，改完自检三要素全部不成立，再走新版本提交；对处置有异议走「联系运营」/ openworkbuddy@tencent.com 申诉，并留存下架通知截图与资产 ID。

## 📚 真实驳回/下架案例库（实测沉淀，提审前逐条对照）

### 案例 1：签到助手强制下架（2026-10-26，公约 2.8.3）
- 平台原文：「涉及通过自动化方式替代用户真实操作，获取平台活动权益」——已发布后巡查下架，非驳回。失误归类：**功能定位**。规则见上文红线节（三要素判定 + 提醒型/查询记录型/手动确认型改造）。

### 案例 2：display_name 平台唯一性（2026-10-27，9 支同日解析失败）
- 报错原文：「解析失败：该名称"<显示名>"已被使用，请修改 SKILL.md 中的 display_name（需在同类型资产中保持唯一）后重新提交」
- 中招：Word 文档处理 / PDF 文档处理 / PPT 演示文稿 / Excel 表格处理 / 合同审查 / 录音转会议纪要 / 述职报告 / 周报日报生成 / 论文排版——全是市场头部同名（别人先占了）。
- 失误归类：**命名**。按 SkillHub 经验套用「纯搜索词名」，没预判 WorkBuddy 的全平台唯一性规则（SkillHub 无此规则，两边不可混用）。
- 定版规则（2026-10-27 lhg 拍板修订）：WorkBuddy 显示名优先用**空格增减**做最小差异化——判重是精确字符串口径（实测「PDF文档处理」去空格版解析通过）：带空格的删空格（Word文档处理/PDF文档处理/Excel表格处理/PPT演示文稿），没空格的在词间加空格（合同 审查/述职 报告/论文 排版/周报日报 生成/录音转 会议纪要）；仍撞名再走词内扩展。禁用「（本地版）」类后缀（lhg 否）。SkillHub 无唯一性规则，保留纯搜索名。仓库 display_name 为 WorkBuddy 版，SkillHub 版打包时还原。

### 案例 3：跨技能引用被判「内置文件缺失」（2026-10-27，3 支审核驳回）
- 驳回原文（评级结论统一为「内置文件缺失」）：发票识别报销——「资产包缺少必需资源 2 项：技能 lls-pdf（SKILL.md 引用）；技能 lls-xlsx（SKILL.md 引用）」；标书检查——引用底座 lls-docx/lls-pdf；课件制作——引用 lls-pptx 及文件 ../lls-pptx/scripts/pptx_create.py。
- 平台文件质量检测会把 SKILL.md（及包内文件）中出现的**其他技能名、包外相对路径**一律当作必需内置资源，缺失即驳回。
- 失误归类：**架构表达**。「底座+场景组合」只写进了技能文本，没料到检测口径——组合关系是产品叙事，不是包内依赖。
- 定版规则：①包内任何文件禁止出现其他技能的 slug 与 ../ 跨包路径；提审前跑跨引用扫描（grep 其他 slug + ../）清零再打包；②跨技能协作一律用通用能力名词表述（如「交给 PDF 文档处理技能」），不写 slug、不写路径；③单技能必须自包含可独立运行，渲染/提取等下游动作写成「如已安装 X 技能则交给它，未安装则交付中间产物」。

### 案例 4：引用清理不能只换名词——必须零提及（2026-10-27，docx 实测）
- 「（本地版）」版 lls-docx 提审后仍被判「内置文件缺失」：检测器把正文里出现的**其他技能的显示名**（如「PDF 文档处理技能」这种通用名词形式）同样识别为资源引用。只把 slug 换成通用名词不够。
- 定版规则：包内文件（SKILL.md/scripts/references/json）对其他技能**零提及**——不写 slug、不写显示名、不写「交给 X 技能/走底座 X」句式；协作步骤一律改写为无主语的动作本身（「渲染成图抽查」「先提取为纯文本」）。自指（本技能自己的名/slug）不受影响。提审前扫描口径：其他技能的 slug + 显示名（含空格/无空格两种形态）在本包内必须为 0。

### 案例 5：重新提交版本号必须严格递增（2026-10-27，B/C 组实测）
- 报错原文：「解析失败：包内版本号 "1.0.0" 必须大于当前最新版本 "1.0.0"：请将 SKILL.md 中的 version 递增后重新打包上传」——已驳回资产的重新提交、审核中资产撤回后的重提，都按「新包 version > 平台最新版」校验；改包必同步递增 version（补丁位 +1 起）。

### 案例 6：账号每日提交审核次数上限（2026-10-27 实测）
- 报错原文：「已达今日技能提交审核次数上限，请明日再来」——当日成功提交约 9 支后触发，触发点在向导步骤 3 点提交时；触发后必须全停，次日再续。
- 定版规则：批量提审按天分批排期（单日预算 ≤9 支留余量）；被上限拦下的资产会停在草稿且已上传的包保留，次日从向导直接续提，先紧着这类半成品，再排新提交与换版重提。
